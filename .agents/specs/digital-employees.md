# Spec：数字员工（Digital Employees）

状态：已评审（2026-11-11，与 OKR [2026-Q4](../okr/2026-Q4-digital-employees.md) 对齐）
关联：[TDD plan](../plans/digital-employees-tdd.md)（交叉验证矩阵见文末）
底座：现有 `packages/experimental/pi-agent/`（RPC 子进程管理、指针注册表、`pi_agent` 工具）全部复用，本 spec 在其上新增员工层。

## 1. 术语

| 术语 | 定义 |
|---|---|
| **数字员工**（employee） | 用户创建的具名 pi 编码代理实体：`{ id, name, description, cwd, piSessionFile? }`。`piSessionFile` 为空表示首次对话时新建 pi 会话并回填；非空表示绑定已有 pi 会话文件（导入）。 |
| **员工会话**（employee session） | 绑定到某员工的 dsh 会话，位于命名会话分组"我的数字员工"下；用户在其中的消息直通该员工绑定的 pi 子代理。 |
| **直通**（passthrough） | 员工会话的用户消息不经过 dsh 主 LLM；由插件转发给 pi 子代理，pi 回答回写为该会话的助手消息。 |
| **数字管理员**（admin） | 管理层员工类型：与用户钉钉账号 IM 通信，接收绑定员工的反馈并转发，经 LLM 工具调用创建/销毁/派活/查询员工。 |
| **绑定**（binding） | 员工记录上的 `managerId`：一个数字管理员管理一个或多个员工；每个员工至多一个管理员（v1）。创建即绑定，销毁即解绑。 |
| **通道**（channel） | 管理员的 IM 实现维度（`dingtalk`，后续 `feishu`）；职责逻辑与通道解耦，收发抽象为可替换 Transport。 |
| **反馈**（feedback） | 被绑定数字程序员的会话回合结算事件：最后的回答文本经管理员层转发到用户钉钉。 |

## 2. 用户场景

### S1 创建员工（UI 向导，2026-11-12 修订）

侧边栏"我的数字员工"分组头的 `+` 按钮弹**新建菜单**（产品级分组头扩展 slot，§3.6）；菜单当前一项：**数字程序员**（员工类型，后端 = pi）。选择类型后弹设置对话框，字段：

| 字段 | 形态 | 默认 |
|---|---|---|
| 名字 | 必填文本 | "数字程序员 N"（N 递增） |
| 头像 | 预设 emoji 徽章集（~12 个）+ 自动分配主题色圆形底；v1 不做上传 | 类型预设 emoji，可换 |
| 工作目录 | 必填，目录浏览 | 分组 workspace 目录 |
| 默认模型 | 下拉，选项经 `employee/piModels` 从 pi 实拉（`get_available_models`），缓存于 Host 生命周期 | pi 自身默认（首项占位"跟随 pi 默认"） |
| 思考强度 | 下拉：跟随默认 / off / low / medium / high | 跟随默认 |

职责描述由类型模板填充（"你是数字程序员，负责编码任务…"），对话框不暴露；`/new-employee --description` 仍可覆盖。导入已有 pi 会话不进 UI（命令保留）。确定后：员工写入目录并**立即创建绑定会话**，分组下出现以员工名命名、带头像徽章的会话入口。

### S2 与员工对话

用户点开员工入口进入员工会话，发送消息：

1. 插件确保该员工的 pi 子代理存活（已绑定则 `--session` 冷恢复，未绑定则新建会话并回填绑定）；
2. 首次新建 pi 会话时，先以一条内部 sendPrompt 注入员工职责描述作为开场指令；
3. 用户消息 sendPrompt 给 pi；pi 回答（`agent_settled` 后的 lastAssistantText）回写为员工会话的助手消息；
4. 运行期间会话显示运行状态；用户可中断（clear_queue + abort），中断后已产生的回答照常回写。

### S3 编辑与删除

- 编辑：向导复用，改名称/职责/cwd；cwd 变更仅影响后续 pi 子代理启动（活动进程不迁移）。
- 删除：确认弹窗；员工目录项与会话入口移除；pi 会话文件**保留**（用户数据不自动删）。

### S4 重启恢复

Host 重启后：员工目录、分组、会话绑定完整恢复；继续对话走冷恢复续用同一 pi 会话（KR3）。

### S5 数字管理员（2026-11-13 增补）

#### S5.1 创建管理员

创建向导第一步新增类型选择：**数字程序员**（一线执行）/**数字管理员**（管理层）。选数字管理员后字段精简：名字（默认"数字管理员 N"）、头像、默认模型、思考强度——工作目录隐藏（固定为分组目录）。管理员同样获得 pi-as-model 会话（可在 web 直接对话），并按 `channel: dingtalk` 接入 IM 通道。

#### S5.2 反馈转发（单向通知）

被绑定数字程序员的会话回合结算后，管理员层组装 `【数字程序员名】反馈：<最后回答>`（超 2000 字符截断）经钉钉 IM 发给用户。发送失败退避重试 3 次，仍失败写 Host 日志并 toast，不阻塞员工继续工作。管理员的创建/销毁动作同样 IM 通知用户（生命周期审计）。

#### S5.3 双向指令（白名单 + 工具调用）

用户在钉钉回复管理员消息：先过 userId 白名单（settings 配置，非白名单一律忽略），通过后注入管理员的 dsh 会话作为指令；管理员 LLM 经工具调用执行，回复文本回发用户钉钉（对话闭环）。工具集 v1：

| 工具 | 语义 | 强制约束（工具实现内，不由 LLM 保证） |
|---|---|---|
| 创建数字程序员 | 按名字/工作目录创建并**自动绑定**本管理员 | 绑定写入即生效 |
| 销毁员工 | 删除指定员工 | **仅限 `managerId` 指向本管理员的员工**；未绑定拒绝；销毁自动解绑 |
| 列出员工 | 名字/类型/状态（运行中/空闲）/最近反馈摘要 | — |
| 派活 | 将消息注入指定已绑定员工的会话 | 仅限已绑定员工 |
| 查询中间状态 | 指定员工的运行/空闲、最近反馈、最后活跃时间 | 仅限已绑定员工 |

#### S5.4 IM 通道（Transport）

收发抽象为 `DingtalkTransport` 可替换接口。v1 落地 dws 实现：发送到私人通知群（`dws chat`，以用户身份），接收经 `dws event` 个人长连接（Host 侧子进程管理，断线重连）。企业内部机器人应用（appKey/appSecret + userId 入 settings，通知以"数字管理员"身份 DM）作为第二实现，配置即切。

#### S5.5 创建/销毁路径

- dsh 侧：向导/命令创建员工时自动绑唯一管理员（多个则向导选择）；删除员工自动解绑。
- IM 侧：经 S5.3 工具，语义同上。
- 管理员自身删除（dsh 删除流）：其绑定员工 `managerId` 清空（解绑不删除）。

## 3. 行为规格

### 3.1 员工目录（EmployeeStore）

- 存储：`$DSH_HOME/pi-agent/employees.json`，原子写（`dsh-atomic-write`，0600）。
- 记录：`{ id: <8位随机>, name, description, cwd, piSessionFile?: string, createdAt }`。
- 校验：name/description 非空；cwd 必须是已存在目录；导入的 piSessionFile 必须指向已存在文件；畸形文件响亮失败（同 children.json 策略）。
- 变更即持久化；读取在插件启动时一次完成。

### 3.2 分组与会话绑定

- "我的数字员工"是**命名会话分组**，不修改全局 "Ungrouped" 文案。
- 员工的 dsh 会话建立绑定时进入该分组；绑定关系持久（会话日志/插件存储）。
- 员工会话在 UI 中显示员工名（会话标题默认取员工名）。

### 3.3 直通语义（passthrough）

- 员工会话的 user message 提交后**不发起 dsh 主 LLM 请求**；插件负责转发并回写答案。
- 回写内容：pi 的最终回答文本（bounded，复用 MAX_RESULT_CHARS）。
- 中断：暴露为会话级停止按钮语义（触发 pi interrupt）。
- 现有 `pi_agent` 五操作工具保持不变，仍可在普通会话中使用（匿名委派逃生门）。

### 3.4 API 面（Remote methods）

`employee/list`、`employee/create`、`employee/update`、`employee/delete`：参数与 §2 场景一致；错误码可定位（名称重复、cwd 不存在、导入文件不存在等）。

### 3.5 UI

- 分组头部"新建数字员工"按钮 → 向导弹窗（表单校验内联显示）；类型步骤见 S5.1。
- 员工会话入口：员工名 + 运行状态点（idle/running/inactive）。
- 全部文案走 locale 字典（8 语言：en/zh/ja/es/fr/de/ru/pt）。

### 3.6 类型与通道体系

- 员工记录：`type: 'pi-coder' | 'admin'` + 管理员专有 `channel: 'dingtalk'`（后续 `'feishu'`）+ `managerId?: string`。
- 类型预设：pi-coder 沿用既有模板；admin 模板职责描述（"你是数字管理员…"）+ 预设 emoji。
- 管理层职责逻辑（绑定/转发/权限）与通道实现解耦：通道只决定 Transport 选择。

### 3.7 绑定模型

- 创建员工（向导/命令/管理员工具）时自动绑定：唯一管理员自动绑，多个则显式选择。
- 销毁员工自动解绑；销毁管理员清空其全部绑定员工的 `managerId`（解绑不删除）。
- 管理员工具的销毁仅限 `managerId` 指向自身的员工；dsh 侧人工删除不受限（所有者是人）。

### 3.8 反馈与 IM 管线

- 事件源：员工会话回合结算（pi 子代理 settle，插件 manager 已观察）。
- 管线：结算 → 按 `managerId` 定位管理员 → 组装消息 → `DingtalkTransport.send`；重试 3 次退避；通道级配置（通知群 id、userId 白名单）入 dsh settings。
- 接收：`dws event` 长连接子进程（随插件启停、断线重连）→ 白名单过滤 → 注入管理员会话（复用直通 adapter 的 prompt 路径）→ 回答回发 IM。

## 4. 非目标

同 OKR 非目标；另：v1 不做员工头像/品牌化、不做员工使用统计；钉钉侧不做企业机器人应用实现（Transport 接口就位）、不做群聊多成员指令、不做反馈的持久化补发队列。

## 5. 开放问题（进入 plan Stage 0 spike 解决）

- Q-A：会话侧边栏命名分组能否由 Host/Client 插件注入？具体扩展点？
- Q-B："直通"的最佳实现缝：agent waterfall 拦截（`agent/pre-step`/`agent/request`）、专用 agent preset、或 client 侧专用视图？dsh 会话基础设施（日志/历史/搜索）必须完整复用。
- Q-C：员工会话的绑定关系存哪（会话事件 vs 插件存储）以同时满足"会话可搜索"与"重启恢复"。
